# Database migrations and demo data

Liquibase starts from `backend/app/src/main/resources/db/changelog.xml`, which includes ordered, versioned changelogs under `db/changelog/`. Each changelog references a focused SQL file under `db/`. The original schema migration remains unchanged and retains its logical path and accepted historical checksum, so existing databases do not replay it. New schema changes should use a new numbered changeset; never edit an applied migration.

Schema migrations apply without a context. Demo changesets use the explicit `@dev` context and run only when `migrationContexts: dev` is configured. They add four fictional identities, six published listings, a draft, example interests and deterministic suggestions. The six bundled PNGs are labelled illustrations, not photographs. Existing listing edits are not overwritten, and the demo rows are not recreated on every startup. The existing development identity reconciliation still restores the known demo accounts and credentials.

The API copies demo illustrations to the configured photo directory only when migrations are enabled and the development context is selected. Existing files are never overwritten. Production configuration must omit the `dev` context, disable demo identity provisioning, and provide its own database, identity, credentials, storage and deployment safeguards. This repository does not yet ship a production deployment configuration. Migrations are forward-only; back up production data and review changes before rollout rather than relying on automatic destructive rollback.

Local development starts migrations with the API. Run Java tests with the commands in the README. Integration tests that exercise migrations use explicitly selected isolated MySQL databases; see `DemoSeedIsolationIntegrationTest` and `DatabaseMigrationsIntegrationTest`. They do not require a Docker socket inside the backend.
